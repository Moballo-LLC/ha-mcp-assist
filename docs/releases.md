# Releases

HA MCP Assist uses GitHub releases for release notes and HACS package delivery.
The repository does not maintain a separate `CHANGELOG.md`.

## Release Notes

Release notes are generated by GitHub from merged PRs using:

```text
.github/release.yml
```

To keep release notes useful:

- Use clear PR titles.
- Keep PRs small and atomic.
- Apply labels consistently when release-note grouping matters.
- Put user-facing context in the PR body when a title alone is not enough.
- Keep the catch-all category title reader-friendly. This repo uses
  `Included Changes` instead of GitHub's more generic `Other Changes` wording.

The final GitHub release body should be edited after generation to use this
shape:

1. A short bulleted list of high-level notable changes.
2. A `---` separator.
3. The full generated changelog.

Do not add a separate `CHANGELOG.md` just to satisfy this format.

## Version Source

The integration version lives in:

```text
custom_components/mcp_assist/manifest.json
```

The release workflow requires the Git tag version to match the manifest version.

Example:

- manifest version: `1.0.0`
- tag: `v1.0.0`

## Release Workflow

The release workflow lives at:

```text
.github/workflows/release.yml
```

On `v*` tags, it:

1. Runs HACS validation against the tagged commit.
2. Runs Hassfest against the tagged commit.
3. Checks that the tag starts with `v`.
4. Checks that the tag version matches `manifest.json`.
5. Checks that the tagged commit is reachable from `origin/main`.
6. Runs the local verification suite.
7. Builds and verifies `dist/mcp_assist.zip` from
   `custom_components/mcp_assist`.
8. Publishes the GitHub release.
9. Attaches the HACS zip artifact.

The package job intentionally reruns validation even if the release commit was
already green on `main`. That keeps tag-triggered publishing from relying on
stale or skipped checks.

## Local Verification

Before running the local CI mirror, create and activate a virtual environment
to keep test dependencies isolated:

```bash
python3.14 -m venv .venv
source .venv/bin/activate
scripts/install_test_dependencies.sh
PYTHON=.venv/bin/python scripts/verify_local.sh
```

The installer resolves the latest stable Home Assistant release and a matching
published test harness from PyPI metadata.
The release workflow resolves that same default environment, selects its
Python version, and installs the selected Core conversation dependencies from
its manifest before running release-candidate validation. Resolution and
installation share one saved version snapshot. Verification explicitly uses
the interpreter selected by CI, including when a future release needs a newer
Python minor. Existing tags created before the resolver was added retain
their original Python 3.14 and pinned-requirements setup when manually
packaged through the current workflow.
The verification script uses `PYTHON` when set; it runs Ruff, Python
compilation, JSON validation, checks that integration runtime requirements do
not duplicate direct Home Assistant Core dependencies, `git diff --check`, and
the full pytest suite with a JUnit file under `test-results/`.

For focused CI-equivalent slices:

```bash
scripts/verify_local.sh --static
scripts/verify_local.sh --pytest
```

### Home Assistant Version Matrix

CI discovers the latest non-yanked stable patch from each of the three most
recent Home Assistant release months. It runs the full `tests` suite on every
selected release. There is no maintained HA version list or harness version
pin. Beta releases and yanked distributions are excluded. Discovery failures
and failures in any matrix row fail the aggregate `Test` check. The workflow
runs daily so new stable releases enter coverage automatically.

For each selected Core release, the resolver checks published package metadata
for a matching `pytest-homeassistant` release. When available, it uses that
official Core test package. Older releases use a published
`pytest-homeassistant-custom-component` harness whose metadata pins that exact
Core release. Missing compatible packages fail the row; CI never downgrades
Core or skips tests to produce a passing check. The two plugins supply
overlapping fixtures, so the installer removes the other plugin when switching
environments. Tests import shared helpers through a small compatibility module.
Pytest disables the standalone respx plugin so Core can install its HTTP alias
before respx loads, as the official harness requires.

`default` and `latest` both resolve the newest stable Core release and matching
harness dynamically. An exact Core target remains available for reproduction;
`--expected-harness` additionally checks a specific harness version. The
installer resolves dependencies together, reads conversation dependencies from
the selected Core manifest, runs `pip check`, and verifies installed Core and
harness metadata against the snapshot.

Each row saves an environment artifact before installation containing the exact
Core version, harness package/version, and Python minor. Installation uses that
snapshot, so newly published releases cannot change the selected pair halfway
through a job. CI selects Python from the packages’ declared requirements.
Local validation may retain ignored environments and receipts under
`.local/validation/`; use separate environments for different Core releases.

To inspect the current matrix or resolve a local environment:

```bash
python scripts/test_environment.py matrix
python scripts/test_environment.py resolve latest --output ha-test-environment.json
```

Create a fresh virtual environment with the Python minor recorded in the
snapshot, then install and test that exact pair:

```bash
scripts/install_test_dependencies.sh --environment ha-test-environment.json .venv/bin/python
.venv/bin/python -m pytest -ra --junitxml=test-results/pytest.xml tests
```

Keep the snapshot for reproduction; resolving `latest` again later may select a
newer release. These three sampled months do not claim full-suite coverage
across the entire Home Assistant 2024.1+ runtime support floor. Existing
runtime compatibility shims and the declared support floor remain unchanged.

Before creating a release tag, run the release-candidate gate:

```bash
RELEASE_TAG=vX.Y.Z scripts/verify_release_candidate.sh
```

This runs the local verification suite, validates the manifest version against
`RELEASE_TAG`, builds `dist/mcp_assist.zip`, checks the zip for forbidden cache
or bytecode files, verifies required integration files, extracts the package,
and compiles the extracted integration.

## How to Publish a Release

1. Make sure the release PRs are merged.
2. Update `custom_components/mcp_assist/manifest.json` with the new version
   in its own commit titled with the bare tag, e.g. `v1.11.1`. Title a
   bump-only PR the same way. If the bump rides along with code changes, keep
   the PR's descriptive title and merge it with a merge commit instead of
   squashing, so the `vX.Y.Z` commit is kept.
3. Run `scripts/verify_release_candidate.sh` with the intended tag.
4. Merge the version bump.
5. Confirm CI, HACS, and Hassfest are green on `main`.
6. Create and push a matching tag:

```bash
git checkout main
git pull origin main
RELEASE_TAG=vX.Y.Z scripts/verify_release_candidate.sh
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

7. Watch the **Release** workflow. It creates a draft release titled with the
   bare tag (e.g. `v1.11.1`), attaches `mcp_assist.zip`, then publishes it.
   Releases are immutable once published, so assets can't be added afterwards.
   If the workflow fails before publishing, re-run it and it reuses the draft;
   if a release was published without the zip, release a new patch version.
8. Edit the generated GitHub release body so it starts with notable changes,
   then a `---` separator, then the full generated changelog.

## Versioning Guidance

Use judgment based on user impact:

- Patch: bug fixes, docs, CI, internal cleanup, small compatibility fixes.
- Minor: new tools, new providers, new settings, or meaningful behavior
  improvements.
- Major: breaking changes, migration requirements, or compatibility drops.

Runtime compatibility should stay lenient unless there is a proven reason to
raise a minimum version.

## HACS Package Shape

The release artifact is built from:

```text
custom_components/mcp_assist
```

Do not rename the integration folder or manifest domain as part of a release.
HACS and Home Assistant can display this project as **HA MCP Assist** while the
integration still loads from `custom_components/mcp_assist` with domain
`mcp_assist`.

## Pre-Release Checklist

- `custom_components/mcp_assist/manifest.json` version is correct.
- `scripts/verify_release_candidate.sh` passes locally with the intended tag.
- CI is green on `main`.
- HACS and Hassfest validation pass.
- The release tag will point at a commit reachable from `origin/main`.
- The final release notes include notable changes, a `---` separator, and the
  full generated changelog.
- Any user-facing docs changed with the feature or behavior change.
- Runtime dependency bounds remain as lenient as practical.
